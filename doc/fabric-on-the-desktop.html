Fabric on the COSMIC desktop

Feature map & vision — every fabric capability, its desktop usefulness, how we envision it, and status. Interactive companion to fabric-on-the-desktop.md.

The shape. One daemon (cosmic-fabricd) owns the fabric deployment — the one channel; everything else is a thin socket client. One profile (policy.toml) every surface reads. Three UI surfaces — plus the socket they sit on, a programmatic 4th surface (see the goo appendix). 
  you ─▶ surfaces (loom · kit · session)
            │ unix socket (line-JSON)  ◀── the 4th, programmatic surface
            ▼
      cosmic-fabricd ─REST▶ fabric --serve ─▶ Ollama / Anthropic / …

The workbench (window): Run · Library (curate patterns) · Models (instantiation editor). Power + config; configures the rest.

Quick OS tie-ins: launcher · panel popup · quick-action (Super+Shift+F on the selection). select → inference → review → close.

A lightweight multi-turn chat dialog (fabric sessions). Escalate from a one-off — "↪ Chat" on a result seeds a session.

Roadmap — by value × feasibility

  • Live shakedown of what's built (no new code; needs a monitor).
  • Escalate-from-one-off → a session seeded with a result. done ("↪ Chat" on the loom response + quick-action result).
  • Capability rule + image source — rule + backend done; path-based Image source wired into the loom. Remaining: native picker/thumbnail + click-validation.
  • Audio in / TTS out — the voice loop (fabric does STT + TTS natively). Needs keys.
  • Contexts & strategies — reusable background + CoT strategies.
  • Image generation — two paths: (a) cloud via fabric (add an OpenAI/Gemini key → --image-file + a polymorphic image-response card; small); (b) local, non-fabric (a separate integration to a local ComfyUI/A1111 API — fabric won't proxy it; real new plumbing).
  • goo routing — real agent hand-off, when goo's route layer exists.
The IN/OUT asymmetry. Images in (vision) run locally today (llama3.2-vision), free + private. Images out (generation) are cloud-only through fabric — no local-via-fabric path, so local image-gen means a separate generator integration (roadmap 6b).
APPENDIX · goo — isolated, aspirational, out of scope

goo & the 4th surface

goo is a sibling router, not part of cosmic-fabric — which ships fully without it and depends on nothing goo-specific.

The unpublicized 4th surface: the daemon socket. The three UIs are all clients of one thing — the cosmic-fabricd unix socket (line-JSON). That socket is a surface: the programmatic/headless one, the seam any external automation (goo, a script, an MCP bridge) touches. No special bridge — speak the protocol and you're a client.

opdoes
ping / statushealth; serve + loaded model + GPU%
patterns / models / surfacediscovery: all patterns; vendor→models; the curated active-set
assemblerender a pattern's prompt — no model run
run (+ stream, broadcast, image)execute → result; stream; broadcast to panel; vision via image
fetchURL → markdown (Jina / readability)
fabric_urlthe live fabric REST URL (loopback) — raw-fabric escape hatch
subscribereceive broadcast results (the panel's channel)

Scriptable now — the cosmic-fabric CLI is a thin client of this socket (orchestrated, not raw fabric): echo text | cosmic-fabric run scribe-summarize, cosmic-fabric assemble … < notes, cosmic-fabric fetch URL, cosmic-fabric patterns. Escape hatch: FABRIC_API="$(cosmic-fabric fabric-url)" (hitting fabric directly bypasses the daemon's orchestration).

Two arrows. goo → fabric: goo consumes the socket as a client (inference→run, assemble→assemble). fabric → goo: a "Send to goo" destination that hands an artifact to goo's UI (seeded) for interactive routing — the UI, not the socket; goo as a meta-destination ("let goo route it"). So send-to should allow dispatcher destinations, not just terminal sinks. Both arrows optional. Full design: cosmic-goo-integration.md.
